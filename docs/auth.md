# Authentication & Routing

Users sign up with a username and secret code or "sign in with google" option, select a role (driver or student), and
land on a central routing gate `authenticated_homepage` that dispatches them based on role and setup state.

## Constraints

- Mock emails are generated by appending @gmail.com to 
username as in: username@gmail.com. REFER TO [EDGE CASE 1].
- Role is set once at signup. There is no role-change flow.
- `assignedDriverId` under `students/{userId}` starts as `null` for 
all students and is only written during the 
driver assignment step, never during signup.
- Batch writes are utilized for drivers and student signup:
  - Students: (1) On singup (2) `student_driver_assignment`
  - Drivers: Only on singup. 

## Data
```
users/{userId}
  role: "driver" | "student"
  displayName: string, 
  username: string,

drivers/{userId}
  assignedStudents: <string>[], 
  refreshTime: string // "HH:mm" format, default "19:00"

students/{userId}
  assignedDriverId: string

[polls.md]
drivers/{driverId}/polls/morning
  period: "morning", 
  checkpoints: null, 
  responses: 
    {studentId}: 
      answer: boolean, 
      boarded: false, 
      updatedAt: timestamp 

[polls.md]
drivers/{driverId}/polls/evening 
  period: "evening", 
  checkpoints: <string>[], 
  responses:
    {studentId}:
      answer: boolean, 
      checkpoint: string, 
      boarded: false, 
      updatedAt: timestamp 
```

## Flow

### Signup (username + password)
1. User enters`username`, `password` and selects `role`. Click submit.
2. Call `createUserWithEmailAndPassword` with mock email based on `username`.
3. Existing username is handled by `createUserWithEmailAndPassword`
4. On auth success, BATCHED WRITE:
#### On driver signup — batched write:
```
users/{userId}
  role, displayName, username
drivers/{userId}
  assignedStudents: [], refreshTime: "19:00"
drivers/{userId}/polls/morning
  period: "morning", checkpoints: null
drivers/{userId}/polls/evening 
  period: "evening", checkpoints: []
```

#### On student signup — batched write:
```
users/{userId}          
  role, displayName, username

students/{userId}       
  assignedDriverId: null
```

5. Redirect to `authenticated_homepage` regardless of role.

### Login

1. User enters `username` + `password`.
2. Calls `signInWithEmailAndPassword` with mock email from `username`.
3. Redirect to `authenticated_homepage`.


### Google Signup/Login

1. This handles both singup and login on a single button click.
2. Since its a single function for both singup and login, we therefore identify 
the type of operation before writing to firestore by checking whether a 
`users/{userId}` doc already exists or not.
---

## Edge Cases

### Signup with different addresses but same username
Suppose a@gmail.com does continue with google. His identification is
"a" because we wanted to keep friction little. Now, username=="a" perform regular signup, we use `signUpWithEmailAndPassword` behind the scenes with a@mock_domain. 
The mock_domain must match with gmail.com to prevent this registration
so that we don't have multiple users with same identity (usernames).

## Tasks

#### `authenticated_homepage`

Routing gate. No UI of its own — renders a loading indicator while resolving, then
navigates. Never renders content directly.

```
authenticated_homepage
  │
  ├─ No active Firebase Auth session
  │     -> /login
  │
  ├─ role == "driver"
  │     -> /driver/home
  │
  └─ role == "student"
        │
        ├─ assignedDriverId != null  ->  render poll_widget
        └─ assignedDriverId == null  ->  /student_driver_assignment
```

Reads on load:
- `users/{userId}`
- `students/{userId}` (only if role is student)
- `drivers/{userId}` (only if role is driver)

Both reads should be cached in a provider after first resolution. Do not re-fetch on
every navigation — `authenticated_homepage` may be hit on hot restart, tab switches,
and deep links. Both are handed to the app-level provider after first read.
The provider is the cache — not authenticated_homepage itself.

#### `student_driver_assignment`

One-time setup. Student enters a driver ID to link themselves.

1. Student enters driver ID.
2. Validate `drivers/{userId}` exists — show inline error and stop if not found.
3. If valid -> Batched write:
```
students/{userId}
  assignedDriverId: driverId

drivers/{driverId}
  arrayUnion(studentId) on assignedStudents

drivers/{driverId}/polls/morning 
  responses:
    {studentId}:
      answer: null,
      boarded: false, 
      updatedAt: now 

drivers/{driverId}/polls/evening 
  responses: 
    {studentId}:
      answer: null, 
      checkpoint: null,
      boarded: false, 
      updatedAt: now 
```
4. On success, redirect to `authenticated_homepage` whose job is to then route to `poll_widget`.
